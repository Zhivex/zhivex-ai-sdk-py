# Zhivex AI SDK 0.15.0 Release Plan

`0.15.0` adds beta durable workflow graphs while preserving the stable agent runtime and existing declarative workflow agents. The release focuses on durable execution mechanics rather than introducing a distributed scheduler.

## Included Work

- `WorkflowBuilder` and `WorkflowGraph` validate acyclic graph definitions, explicit entrypoints, reachability, edge identity, and unique state outputs before execution.
- Ready nodes execute in bounded parallel waves; conditional edge decisions are checkpointed before downstream dispatch and are not re-evaluated during resume.
- Graph steps can run an `Agent` or a sync/async `WorkflowFunctionExecutor`. Functional steps receive ephemeral dependencies and a stable idempotency key, then return finite JSON output/state patches through `WorkflowFunctionResult`.
- `WorkflowCheckpoint` is the canonical versioned record with append-only transition history, optimistic sequence checks, node status/output, routing decisions, interrupts, resume values, and fork lineage.
- In-memory, SQLite, and optional Postgres workflow checkpoint stores implement the same beta `WorkflowCheckpointStore` contract. SQLite covers process-style reconstruction locally; Postgres targets transactional shared-worker storage.
- `resume_workflow(...)` acknowledges explicit before/after interrupts or continues one suspended agent approval without reconstructing the remaining graph manually.
- `fork_workflow(...)` creates a new run from an immutable checkpoint and records the source run/checkpoint lineage.
- `WorkflowRetryPolicy` retries a complete logical step with stable identity and bounded exponential backoff. Existing `WorkflowStep.max_retries` continues to configure model/provider retries within `run_agent(...)`.
- Idempotent re-entry fails closed while a run is still active; `recover_running=True` is an explicit, recorded takeover after the caller confirms prior-worker loss.
- Existing `SequentialAgent`, `ParallelAgent`, `LoopAgent`, `run_workflow(...)`, workflow result text/state, and replay projection remain available.

## Adapter Boundary

The release includes versioned callback contracts through `WorkflowStepRequest`, `WorkflowStepOutcome`, `WorkflowStepExecutorRegistry`, and `CallbackWorkflowAdapter`.

`create_dbos_workflow_adapter(...)`, `create_temporal_workflow_adapter(...)`, `create_prefect_workflow_adapter(...)`, and `create_restate_workflow_adapter(...)` provide dependency-free envelopes and conservative capability metadata. They are not certified DBOS, Temporal, Prefect, or Restate integrations and do not install, start, schedule, persist, signal, or operate those engines. Applications own the real engine callback and its end-to-end tests.

## Compatibility And Migration

- All new workflow graph, checkpoint/store, retry, functional-step, resume/fork, and adapter APIs are beta.
- Existing declarative workflow constructors and `WorkflowStep` positional agent usage remain compatible; new fields are additive.
- Functional executors are graph-only. Existing sequential, parallel, and loop agents continue to require an `Agent` per step.
- Resume and fork require the same workflow name, `definition_version`, and computed definition digest. Definition drift fails closed.
- Checkpoint and adapter envelopes have independent schema versions. Unsupported future versions are rejected.
- There is no automatic checkpoint migration engine in `0.15.0`. Applications must preserve source history and explicitly audit any migration.

## Security And Operations

- Workflow state, output, interrupt payloads, and resume values can contain sensitive or regulated data. Applications own encryption, tenant authorization, retention, deletion, archival, and backups.
- Runtime dependencies, clients, credentials, transactions, agents, and callables are not durable state and must be supplied again after resume.
- A checkpoint append is not a distributed transaction with an external write. Tools, functional steps, and adapter activities must use the logical step idempotency key, an outbox, or reconciliation/compensation.
- `recover_running=True` must be used only after proving that the prior worker is no longer active. It cannot resolve an unknown external outcome by itself.
- In-memory storage is process-local. SQLite durability depends on local filesystem operations and backup. Postgres behavior must be tested against the deployment database and failure model.
- The `AgentRunState` snapshot remains a replay/observability projection; `WorkflowCheckpoint` is authoritative for workflow recovery.

## Release Evidence

Before publishing, run:

```bash
make test-agent-contracts
make test-agents
make test-examples
make test-contract
make test-docs
make typecheck
make check
make release-check
make release-evidence
.venv/bin/python examples/agents/durable_graph_workflow.py
```

Verify the release tag against package metadata:

```bash
.venv/bin/python scripts/verify_release_tag.py --tag v0.15.0
```

The release candidate must pass the existing Postgres run store suite for stable agent idempotency, durable approvals, resume, and terminal-state behavior. It must also run the workflow checkpoint integration suite with `ZHIVEX_TEST_POSTGRES_DSN` against PostgreSQL; a deferred-import/mock-only test is not live database certification.

Build and install the wheel and source distribution in fresh environments. The artifact smoke must import the beta workflow graph/checkpoint surface and execute an offline graph transition. Optional provider smoke remains separate and must record every skipped credential/model path rather than presenting it as live certification.
