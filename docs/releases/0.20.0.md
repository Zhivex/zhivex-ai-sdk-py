# 0.20.0 Release Plan

Version `0.20.0` promotes the SDK-owned workflow orchestration cohort to Stable, adds explicit checkpoint migration, and closes the Meta exact-artifact certification gap left by `0.19.0`. The distribution remains a Beta package; this is an API-cohort promotion, not package-wide GA.

## Scope

- Stable declarative workflows, durable DAGs, functional steps, retries, interrupts, resume/fork/cancel, typed workflow failures, and the engine-neutral callback envelope
- Stable in-memory, SQLite, and Postgres checkpoint stores plus lease managers, heartbeat, fencing, recovery, and atomic fenced appends
- checkpoint schema v2 with auditable `migration_history`
- pure v1→v2 value/payload migration and CAS-backed stored-run migration
- Beta DBOS, Temporal, Prefect, and Restate named adapter factories; no claim of certified third-party engine integration
- exact-wheel release smoke policy requiring cost-oriented OpenAI Luna and Meta Contributor targets
- sanitized evidence containing source revision, wheel filename/SHA256, provider, model, and executed operations

## Compatibility Boundary

- Published schema-v1 checkpoints remain readable and canonically serializable.
- Existing v1 runs can still resume/fork directly; operators may explicitly append a v2 migration before continuing.
- Stored-run migration is allowed only for non-terminal history and uses the same optimistic sequence boundary as workflow progress.
- Definition version/digest checks remain unchanged. Checkpoint migration does not migrate graph definitions, external effects, or third-party engine state.
- Stable workflow APIs follow the deprecation policy in `VERSIONING.md`; the four named engine factories retain Beta minor-release flexibility.

## Required Evidence

- workflow compatibility fixture: v1 read/reserialize, direct resume/fork, deterministic migration, and post-migration resume
- in-memory and SQLite checkpoint/lease/CAS/fencing/recovery suites
- Postgres source integration tests against the configured deployment-compatible service
- installed-wheel Postgres workflow smoke with checkpoint reload, history, fencing token, and cleanup
- existing Stable infrastructure, including the Postgres run store, remains green
- public stability manifest, transitive workflow annotation gate, public root snapshot, and generated type stub agree
- `make check` and `make release-check` pass for the candidate
- the protected release environment runs the installed wheel under `docs/releases/0.20.0-smoke-policy.json`
- OpenAI `gpt-5.6-luna` passes generation and an agent tool loop with reasoning effort `none`
- Meta Contributor `muse-spark-1.2-contributor` passes generation, streaming, structured output, portable retrieval, and an agent tool loop using synthetic marker-only prompts. Its canary keeps `reasoning_effort="low"` and a 512-token output ceiling: live Contributor streaming can spend more than 128 output tokens on hidden reasoning and otherwise complete without a visible text delta.
- the uploaded smoke evidence records the exact wheel SHA256 and source revision without credentials

The Contributor target is an explicit cost optimization for non-sensitive release canaries. It remains Beta, has different data-use terms, and does not certify the Stable Standard `muse-spark-1.2` route. A Standard certification claim still requires a separate exact-artifact run naming that model.

Capture local candidate evidence with:

```bash
make release-evidence
```

Local or dirty-worktree results are integration evidence. Formal release certification exists only after the exact clean tagged artifact passes the protected workflow and the evidence artifact is retained.

## Production Boundary

Applications still own authentication, tenant authorization, retention, backups, data classification, deployment-specific Postgres contention tests, and business audit policy. Durable checkpoints cannot make arbitrary provider, database, or API side effects atomic; nodes must use destination idempotency, fencing, an outbox, compensation, or reconciliation.
