# 0.28.3 — OpenAI response recovery and Luna 6 canary

This Beta candidate carries the [0.28.0 feature scope](0.28.0.md) and fixes the
OpenAI response normalization regression that blocked 0.28.2 publication.
Public imports, compatibility policy and provider stability classifications
remain unchanged.

## Problem and correction

The protected [0.28.2 release](https://github.com/Zhivex/zhivex-ai-sdk-py/actions/runs/36865794454)
passed build and release gates, but its OpenAI generation smoke returned empty
normalized text. Meta passed; certification validation and PyPI publication
were skipped. Local probes with the exact CI wheel reproduced the issue with
both `gpt-5.6-luna` and `gpt-6-luna`: the provider returned the expected text in
an ordinary assistant message with `phase="final_answer"` and no `agent` field.
The SDK incorrectly classified that message as hosted multi-agent output and
discarded its text.

The normalizer now requires agent attribution or a collaboration item type to
infer hosted multi-agent output. Ordinary generation and streaming preserve
final-answer text. Explicit multi-agent requests still require an attributed
root final answer and continue to filter subagent, commentary and ambiguous
output. Regression tests cover ordinary messages and the existing multi-agent
filtering and replay contracts.

## Release controls

Package metadata, lockfile, README and both publication workflows select
`0.28.3`. The [protected smoke policy](0.28.3-smoke-policy.json) selects OpenAI
`gpt-6-luna` for generation and agent-tool, with reasoning effort `none` in both
flows. Meta remains `muse-spark-1.2-contributor` with generation, streaming,
structured output, portable retrieval and agent-tool requirements.

Installed-wheel checks, artifact SHA256 evidence, protected environments and
certification validation remain required. Historical 0.28.2 notes, policy and
tag remain unchanged; their wheel and evidence do not certify 0.28.3.

## Validation and release sequence

Run `make release-check` and `make release-evidence` to record local checks and
artifact hashes. The Postgres run store and installed durable workflow gates
must run with a configured database. Local provider probes, skipped database
checks and a dirty-tree build do not prove protected certification or PyPI
publication. The local [release evidence](0.28.3-evidence.md) records its scope.

Review this change through a PR and verify CI on the merged `main` commit.
Before creating a fresh annotated `v0.28.3` tag, verify
`python scripts/verify_release_tag.py --tag v0.28.3` and confirm the tag does not
already exist remotely. Push the tag only on that reviewed merged commit.
The protected publication workflow must build and certify the exact tagged
artifact before publishing. Confirm PyPI availability after the workflow
succeeds. This preparation does not create a tag or publish a package.
